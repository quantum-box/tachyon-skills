# Incident Report

障害・脆弱性の報告を、業務上の状況を知りたい読者にも、技術的な根拠を確認したい読者にも伝わる形に整える。特定の製品・リポジトリに限定しない。出力言語はユーザーと既存文書に合わせる。

## 情報を整理する

- 既存文書を直す場合は、まず最新の本文とプロパティを読む。執筆・要約の依頼だけで新たな監査、復旧作業、デプロイを始めない。
- 根拠から、問題の内容、対象、利用者への影響、実施済みの対応、未完了の対応、確認範囲を分ける。不明な点は不明として扱う。
- 提供された事実を読みやすくする作業と、最新状況を調べ直す作業を混同しない。過去の調査結果は確認時点が分かる表現にする。新たに版番号や脆弱性情報を調べる場合は公式情報で確認する。
- 「設定変更済み」「テスト済み」「試験環境へ反映済み」「本番へ反映済み」「本番で動作確認済み」を区別する。一部の環境の成功を、全環境の対応完了に広げない。

## 基本説明を先に置く

標準の構成は次の通り。既存の見出しやユーザー指定に合わせて統合・省略してよい。

1. **概要** — 何が起きたか、対象と影響、現在の対応状況を短く伝える。
2. **対象技術とは** — 理解に必要な場合だけ、その技術が何に使われているかを説明する。見出しは「Node.jsとは」のように対象の名前にする。
3. **対応状況** — 実施済みと未完了を、製品や対応項目ごとに簡潔に記載する。
4. **安全性の確認と今後の対応** — 確認できたこと、調査の限界、残る対応をまとめる。通常の障害なら「影響の確認と今後の対応」など内容に合う名前にする。
5. **技術情報** — 版番号、調査条件、ログの範囲、配備根拠、技術上の残件、参照先を末尾にまとめる。

- 前半だけで状況と残件が分かるようにする。基本説明と技術情報で、長い説明を繰り返さない。
- 「技術に詳しくない方へ」「非エンジニア向け」のように読者を分類する見出しは付けない。
- 前半では「ビルド」を「公開するプログラムの作成」、「デプロイ」を「本番への反映」のように言い換える。必要な用語だけ初出で短く説明する。
- 後から判明した製品も同じ「対応状況」に含める。編集の経緯だけを理由に「○○への追加対応」という節を増やさない。時系列が理解に必要なときは別途示す。
- 技術情報も生ログの貼り付けではなく、結論を確かめられる最小限の根拠にする。詳しい記録は参照リンクに分け、秘密情報は含めない。

具体的な構成例が必要な場合は [report-template.md](references/report-template.md) を読む。固有名詞・日付・版番号は例から流用しない。

## 確度と限界を保つ

- 脆弱性があることと、悪用・侵害が起きたことを区別する。更新したことも、過去の被害がなかった証拠にはしない。
- 「確認した範囲では直接示す証拠は見つかっていない」を、調査範囲の裏付けなしに「被害なし」「安全確認済み」へ言い換えない。
- アクセス拒否、エラー、HTTPステータスだけで攻撃成功や今回の問題との因果関係を断定しない。
- 技術情報には、結論を制約する対象・期間・サンプル・未調査領域を残す。読みやすさのために重要な留保を削らず、同じ留保の重複を減らす。

## 保存とプロパティ

- 指定された保存先には、利用可能な専用ツールで編集する。下書きだけの依頼なら保存・公開・通知まで広げない。
- プロパティも依頼範囲に含まれる場合は、本文と整合させる。選択肢は保存先で確認し、他案件の選択肢IDを流用しない。
- 発生日時・検知日時・脆弱性の公表日・公開日・復旧日時を混同しない。公表日を「発生日時」とする運用をユーザーが選んだ場合は、その意味を本文に明記する。未確定の日付や時刻を推測で埋めない。
- 復旧日時と「解決済み」は、必要な対応の完了が確認できたときに設定する。対応中なら復旧日時を空欄にするなど、保存先の型に合う未確定表現を使う。
- 本文のみの編集では、ID、対象製品、公開設定、日付など無関係なプロパティを維持する。既存文書の公開状態を変えない。
- 書き込み前に本文が他者に更新されていないか確認し、更新されていれば読み直して編集を適用する。保存後は再取得し、本文と依頼対象のプロパティを確認する。

完了時は、構成や表現をどう変えたかを短く伝える。対応や調査そのものが完了したと誤解させない。
