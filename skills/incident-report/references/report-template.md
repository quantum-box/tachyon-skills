# 報告書の構成例

山括弧内は執筆時に根拠で置き換えるか、省略する。これは構成の例であり、出来事や調査結果を補うための例文ではない。見出しは必要に応じてまとめる。

```markdown
## 概要

<日付・何が起きたか・対象・利用者への影響。>
<現時点の対応状況。確認できていないことがあれば簡潔に示す。>

## <対象技術>とは

<その技術が何に使われているかを、業務やサービスとの関係で説明する。>
<今回その技術のどのような問題に対応しているのか。理解に不要なら節ごと省略する。>

## 対応状況

**<製品・項目A>：**<何を実施し、どこまで確認済みか。>

**<製品・項目B>：**<確認済みの範囲と、残っている対応。>

## 安全性の確認と今後の対応

<調査結果を平易に要約する。調査した範囲と、結論の限界を示す。>

<残る確認・対応。次の報告時期が決まっている場合だけ記載する。>

## 技術情報

**対象・更新内容：**<製品、版番号、構成など。>

**反映・検証の根拠：**<変更、テスト、試験環境、本番反映、本番動作確認を区別する。>

**調査範囲：**<期間とタイムゾーン、対象環境、ログの種類、サンプルなど。>

**制約・残件：**<未調査領域、未完了の経路、判定できていない因果関係など。>

参考：<公式告知やアクセス可能な調査・検証記録へのリンク。>
```

## 同じ事実を説明の深さで分ける例

- 基本説明：公開するプログラムを作る環境を修正版へ更新し、試験用環境で動作を確認しました。本番への反映はまだ完了していません。
- 技術情報：対象ランタイムの旧版・修正版、テスト結果、プレビュー配備の記録、本番配備が未確認であることを記載する。

版番号や成功したテストの数だけで「復旧済み」としない。同じ環境を再度調査したように見せず、実際に確認した時点と範囲を保つ。
