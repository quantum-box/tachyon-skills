# 判断の型と道具の選び方

## よく出る判断の型と、証明する性質

| 判断の型 | 証明する性質の例 | 典型的な変異 |
| --- | --- | --- |
| 照合・包含（TRN、scope、承認範囲） | 許可 ⇔ 要求が許可集合に含まれる。同値表記を同じに扱う | 常に許可、wildcardを特別扱いしない、prefix一致に緩める |
| 集約（Allow/Deny、複数grant） | Denyが1つでもあれば拒否。Allowは対象一致が必要 | Denyを無視、any/allの取り違え |
| 上限（付与・編集） | 付与後の権限 ⊆ grantorの権限 | 上限検査を外す、pattern展開前の比較 |
| 束縛（tenant/app/child、口座） | 操作対象 = 認可した対象。ずれれば拒否 | ID照合を `true` にする、親だけ照合 |
| 金額算術 | 単位・丸め方向・overflowで拒否、合計の保存 | 飽和演算への置換、丸めを逆にする、境界を1ずらす |
| 状態遷移 | 許される遷移だけを受理する。終端は不変。古い世代は拒否 | 終端からの遷移を許す、世代比較を `>=` にする |
| 再送・冪等 | 同じキーの2回目は1回目の結果を返し、効果は1回だけ | キーを無視、結果不明を成功扱い |

## 道具の選び方

- 1回の呼出しの判断なら、Verusで本番関数を検証する。Rustの既定。
- 複数の呼出しの順序（再送、callbackの到着順、lease、2つの更新の競合）なら、TLA+で設計を有界モデル検査する。
  - そのうえで、各actionを担う本番の関数（Verusで検証できるもの）と、原子性を担うSQL/CASとの対応を表にする。
  - SQLの原子性は、統合テストで競合を再現して確かめる。
- 外部の動作（Stripe、GitHub、Cloud Run、Cognito、JWT署名、時刻）は検証の外に置く。台帳に「信頼する仮定」として書き、呼出元の統合テストで確かめる。

## 純粋でない処理の切り出し方

1. async usecaseの中から、読み取った値だけで決まる判断を、引数と返り値だけの関数に移す。
2. 引数はbytes・整数・Vec・enumにする。ドメイン型からの変換は、本番側のadapterに置く。
3. 返り値は、拒否理由を区別できるenumにする（boolにしない）。エラー優先も証明の対象になる。
4. usecaseは、その関数の返り値で分岐するだけにする。分岐の後に、同じ判断を別の条件で上書きしない。
5. 「読んだ後に状態が変わる」問題（TOCTOU）は、純粋関数の証明では防げない。CAS／条件付きUPDATE／transactionで閉じる。閉じたことは統合テストで示す。
